# Закріплення сертифіката ЦЗО (pinned trust list)

Документ описує, **навіщо** і **як** закріпити сертифікат підписанта довірчого
списку, і що робити, коли ЦЗО його замінить.

## Навіщо це потрібно

Без закріплення Tamga перевіряє підпис довірчого списку лише на
**самоузгодженість**: сертифікат підписанта береться з того самого документа
(`ds:Signature/ds:KeyInfo`), яким і підписано список. Це доводить цілісність, але
**не походження** — зловмисник, здатний підмінити файл, підмінить і сертифікат
усередині нього.

| Статус у звіті | Що доведено |
| --- | --- |
| `not-verified-disabled` | Нічого: перевірку вимкнено |
| `not-verified-unsupported` | Нічого: у цій збірці немає потрібного алгоритму (наприклад, RSA при `TAMGA_ENABLE_VENDOR_CRYPTONITE=OFF` поза Windows) |
| `verified-self-consistent` | Цілісність. **Не** походження |
| `verified-pinned` | Походження: підпис зроблено саме тим ключем, який ви закріпили |

Довірчий список — корінь усієї моделі довіри: з нього матеріалізуються якорі, за
якими потім перевіряються всі підписи. Тому `verified-pinned` — єдиний стан, у
якому ланцюг довіри замкнений.

## Звідки взяти сертифікат

Сертифікат підписанта (`Trusted List Administrator`) **не поширюється** через
`CACertificates.p7b` або `CACertificates.zip` ЦЗО — перевірено пошуком за
відкритим ключем серед 979 унікальних сертифікатів із цих бандлів: жодного збігу.
Він самопідписаний і присутній лише всередині самого довірчого списку.

Тому доступні два шляхи.

### Спосіб 1 — з довірчого списку по HTTPS (поточний)

```bash
curl -sS --fail --proto '=https' --tlsv1.2 \
     -o TL-UA-EC.xml https://czo.gov.ua/download/tl/TL-UA-EC.xml
```

Далі витягти сертифікат із `ds:Signature/ds:KeyInfo/ds:X509Certificate`
(base64 → DER) і звірити відбиток із таблицею нижче.

**Що це дає і чого не дає.** Довіра спирається на TLS до `czo.gov.ua` **у момент
завантаження**. Це суттєво сильніше за самоузгодженість: підміна тепер вимагає
зламати TLS до домену ЦЗО саме тоді, коли ви закріплюєте сертифікат, а не просто
підсунути файл будь-коли пізніше. Але це **не** якір у сенсі PKI.

### Спосіб 2 — з незалежного каналу (бажаний)

Якщо ЦЗО опублікує відбиток сертифіката окремо (регламент, друковане джерело,
офіційний лист) — звірте `sha256` з таблицею нижче. Тільки такий збіг робить
закріплення справжнім якорем довіри.

## Як увімкнути

### З 1С

```bsl
// pinnedCertBase64 — вміст czo-tl-signer.b64 (без переносів рядків)
Компонента.НастроитьДоверенныйСписок(
    "",                 // url: порожній = стандартний ЦЗО
    30000,              // timeoutMs
    24,                 // ttlHours
    ПінКодуванняBase64, // pinnedCertBase64
    "require");         // signaturePolicy
```

Значення `signaturePolicy`:

| Значення | Поведінка |
| --- | --- |
| `disabled` | Підпис TL не перевіряється |
| `prefer-available` | Перевіряти, якщо збірка вміє; інакше пропустити зі статусом `not-verified-unsupported` (**типове**) |
| `require` | Перевірка обовʼязкова: неможливість перевірити обриває синхронізацію |

Для продуктивного середовища рекомендується `require` **разом із** закріпленим
сертифікатом. Без сертифіката `require` дає лише `verified-self-consistent`.

### Перевірити результат

```bash
tamga-interop-diag tl-sig TL-UA-EC.xml tests/fixtures/trust-list/czo-tl-signer.der
# Очікується: RESULT : VERIFIED (pinned origin proven)
```

У звіті синхронізації поле `trustListSync.xmlSignatureStatus` має стати
`verified-pinned`.

## Оновлення після 2027-09-12

Сертифікат чинний до **2027-09-12**. Коли ЦЗО замінить підписанта, закріплений
сертифікат перестане збігатися, і синхронізація довірчого списку **зупиниться**.

Це **правильна** поведінка (fail-closed): краще зупинити оновлення, ніж
прийняти список, підписаний невідомим ключем. Але вона виглядає як раптова
відмова, тому:

1. **Заплануйте перевірку заздалегідь** — щонайменше за місяць до 2027-09-12.
2. Отримайте новий сертифікат (спосіб 1 або 2 вище) і звірте відбиток.
3. Оновіть `pinnedCertBase64` у конфігурації 1С і фікстуру в репозиторії
   **разом із** `PROVENANCE.md`.
4. Перевірте `tl-sig` до розгортання.

### Аварійний сценарій

Якщо оновлення потрібне терміново, а новий сертифікат ще не звірений:

- **не** вимикайте перевірку назовсім (`disabled`) — це знімає захист повністю;
- тимчасово перейдіть на `prefer-available` **без** `pinnedCertBase64`: залишиться
  `verified-self-consistent`, тобто цілісність перевіряється, походження — ні;
- поверніть закріплення одразу після звірки відбитка.

Різницю видно у звіті, тож тимчасовий стан не буде мовчазним.

## Обмеження

- **Поза Windows** RSA-SHA256 доступний у стандартній збірці з vendored
  cryptonite. Діагностичний режим `TAMGA_ENABLE_VENDOR_CRYPTONITE=OFF`
  повертає `not-verified-unsupported`, а `require` обриває синхронізацію.
- Закріплення стосується лише `TL-UA-EC.xml`. Списки `TL-UA.xml` і
  `TL-UA-DSTU.xml` перевіряються на самоузгодженість; окремих закріплених
  сертифікатів для них наразі немає.
