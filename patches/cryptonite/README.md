# Patch queue для cryptonite

Цей каталог містить **іменовані unified diff патчі** для інтеграції `vendor/cryptonite` у `Tamga`.

## Статус

Повний перелік і порядок патчів задає `series.txt`; кількість перевіряє replay-скрипт.

- Upstream зафіксований машиночитно в `upstream.json`:
  `https://github.com/privat-it/cryptonite` @
  `3618d340d22e27a6becf97d89c453f8e64068a39`
  (перевірено 2026-08-30 командою `git ls-remote https://github.com/privat-it/cryptonite`
  → цей SHA є `HEAD` і `refs/heads/master`).
- Рівність `projection(upstream + series.txt) == vendor/cryptonite` перевіряється
  **механічно**: `scripts/verify-cryptonite-patches.ps1`. Успіх = порожній diff.
- `add_subdirectory(vendor/cryptonite)` працює у трьох штатних конфігураціях.

`excluded-paths.json` задає SHA-256 вилучених upstream-файлів після застосування патчів. Поле `source_sha256`, якщо є, зберігає hash початкової локальної копії з її переводами рядків. Потрібні Tamga сертифікати й CRL у `src/pkixUtest/resources` залишено; приватні ключі та невикористовуваний upstream test harness не постачаються. Replay створює ізольований Git-корінь і працює також усередині іншого репозиторію.

## Навіщо це потрібно

Upstream `cryptonite` у поточному вигляді:

- одразу підтягує тести та приклади (11+ subdirectories)
- жорстко додає `-Werror -Wall` що ламає MSVC збірку
- очікує `pthread`-орієнтовану схему збірки
- не адаптований під наш single-binary CMake flow з MSVC

Саме тому потрібна patch queue для чистої інтеграції.

## Опис патчів

### 0001-disable-upstream-tests-and-examples.patch

**Мета**: Вимкнути тестові та прикладні targets при збірці як subdirectory

**Зміни**:
- Додано `CRYPTONITE_BUILD_TESTS` та `CRYPTONITE_BUILD_EXAMPLES` options
- За замовчуванням: `ON` для standalone, `OFF` для embedded
- Обернуто `add_subdirectory()` для тестів у `if(CRYPTONITE_BUILD_TESTS)`
- Обернуто приклади у `if(CRYPTONITE_BUILD_EXAMPLES)`

**Результат**: При `add_subdirectory(vendor/cryptonite)` збираються лише library targets: `cryptonite`, `asn1`, `pkix`, `storage`, `pthread_impl`

### 0002-msvc-warning-and-runtime-compat.patch

**Мета**: MSVC сумісність та налаштування warnings

**Зміни**:
- Додано `CRYPTONITE_STRICT_WARNINGS` option (default: standalone only)
- Розділено компілятор-специфічні прапори для MSVC vs GCC/Clang
- Додано `_CRT_SECURE_NO_WARNINGS` для MSVC
- `-Werror` тепер опційний через `CRYPTONITE_STRICT_WARNINGS`

### 0003-pthread-and-cross-platform-linking.patch

**Мета**: Кросплатформна інтеграція pthread та виправлення збірки

**Зміни**:
- Виправлення pthread_impl для Windows/MSVC
- Налаштування cross-platform linking
- Виправлення race conditions у crypto_cache

### 0004-msvc-asn1-initialization-and-stdint-compat.patch

**Мета**: Прибрати блокуючі MSVC помилки/попередження у ASN.1 коді

**Зміни**:
- Ініціалізація локальних змінних у `src/asn1/c/ANY.c`, щоб прибрати ризик використання неініціалізованих вказівників (`C4703`/`C4701`)
- Перехід на стандартний `<stdint.h>` у `src/asn1/c/asn_system.h` для MSVC замість ручних typedef'ів
- Захист `WIN32_LEAN_AND_MEAN` через `#ifndef`, щоб уникнути масових `C4005`

### 0005-msvc-pkix-utils-and-tag-type-warnings.patch

**Мета**: Прибрати MSVC-попередження у PKIX utility/tag code без зміни зовнішньої поведінки

**Зміни**:
- Уточнення типів ASN.1 tag-констант для MSVC.
- Локальні compatibility-виправлення для PKIX helper-коду.
- Зменшення шуму warning-ів у production Windows-збірці Tamga.

## Опис патчів (продовження)

Порядок застосування, механічна перевірка і що робити, коли патч не
накладається — у розділі [«Робота з чергою»](#робота-з-чергою) в кінці файлу.
Тримати ці інструкції посередині списку патчів було помилкою: вони
обривалися на `0005`, і читач робив висновок, що черга з пʼяти патчів.

### 0006-dstu4145-with-kupyna-dstu7564.patch

**Мета**: підтримка ДСТУ 4145 з Купиною (ДСТУ 7564) — гілка OID `1.2.804.2.1.1.1.1.3.6.*`.

**Навіщо**: upstream cryptonite знає лише ДСТУ 4145 з ГОСТ 34.311 (`...3.1.*`).
Digest-адаптер PKIX має режими GOST34311 / SHA1 / SHA2 і **не має Купини взагалі**,
хоча примітив `dstu7564_*` у бібліотеці присутній. Через це валідні PAdES/CMS-підписи,
створені сучасними українськими засобами (перевірено на документах Дія:
`digestAlgorithm = 1.2.804.2.1.1.1.1.2.2.1`, `signatureAlgorithm = 1.2.804.2.1.1.1.1.3.6.1.1`),
відхилялися як криптографічно невалідні — хибнонегатив.

**Що змінює**:

- `api/oids.h` / `api/oids.c` — нові OID: `OID_PKI_DSTU7564_256` (`1.2.804.2.1.1.1.1.2.2.1`),
  `OID_PKI_DSTU4145_WITH_DSTU7564` (`...3.6`), плюс LE/BE-варіанти `...3.6.1.1` / `...3.6.1.1.1`;
- `crypto/cryptonite_manager.c` — новий режим `DIGEST_MODE_DSTU7564` (alloc/update/final/free)
  і його диспетчеризація в `digest_adapter_init_by_aid`. Купина **не параметризована**
  (ні sbox, ні sync, на відміну від ГОСТ 34.311), тому контекст будується напряму
  `dstu7564_alloc(DSTU7564_SBOX_1)` + `dstu7564_init(ctx, 32)`;
- `digest_adapter_init_by_cert` — для сертифіката, підписаного `...3.6.*`, хеш береться
  з **алгоритму підпису**, а не з SPKI (тип ключа лишається `...3.1.1` в обох випадках);
- `api/aid.c`, `api/pkix_utils.c`, `api/spki.c` — гілка `...3.6` приймається нарівні з `...3.1`
  у перевірках алгоритму підпису; `is_dstu_le_params`/`is_dstu_be_params` розпізнають
  `...3.6.1.1` / `...3.6.1.1.1`.

**Свідомі обмеження**:

- `digest_adapter_copy_with_alloc` для режиму Купини повертає помилку: upstream
  `dstu7564` не експортує `copy_with_alloc`, тож клонувати проміжний стан неможливо.
  Створювати «свіжий» контекст замість копії було б мовчазною підміною (інший дайджест),
  тому обрано fail-closed. Продакшн-споживачів у `pkix` немає — функція викликається
  лише з upstream `pkixUtest`, вимкненого патчем `0001`.
- Нумерація підгілки `...3.6.*` дзеркалить `...3.1.*`. Підтверджено на реальних
  документах для PB LE (`...3.6.1.1`); решта варіантів — за аналогією, без тестових даних.

**Перевірено**: повний CTest 34/34 на статичній збірці; interop-регресія на ГОСТ-артефактах
Дія (ASiC-E, ASiC-S) і двопідписному CMS Вчасно — без змін; PAdES-документи на Купині
більше не відхиляються на етапі CMS.

**Upstream**: доцільно заслати в `privat-it/cryptonite` — це не Tamga-специфічна інтеграція,
а відсутня підтримка чинного національного стандарту.

### 0007-dstu4145-kupyna-verify-adapter.patch

**Мета**: довести підтримку Купини до **верифікаційного** адаптера — доповнення до `0006`.

**Навіщо**: `0006` навчив рахувати Купину `DigestAdapter`, і цього вистачило, щоб збігся
атрибут `messageDigest`. Але сам підпис рахується над `signedAttrs` **всередині**
`VerifyAdapter` (`verify_core` → `va->verify_data`), а там для `alg_marker == DSTU4145`
дайджест був **жорстко зашитий** як ГОСТ 34.311, без жодної залежності від оголошеного
алгоритму. Тому документ на Купині проходив перевірку вмісту й падав на перевірці підпису —
той самий хибнонегатив, лише на крок пізніше.

**Що змінює** (усе в `crypto/cryptonite_manager.c`):

- `va_verify_data` — гілка `DSTU4145` більше не припускає ГОСТ: якщо `digest_aid` адаптера
  вказує на `OID_PKI_DSTU7564_256`, `signedAttrs` хешуються Купиною (`dstu7564_*`),
  інакше — як і раніше ГОСТ 34.311. Контекст Купини звільняється в `cleanup`;
- `va_set_digest_alg` — приймає OID Купини-256 (раніше `RET_PKIX_UNSUPPORTED_DIGEST_ALG`);
- `va_set_digest_alg` — додано гілку узгодженості для ДСТУ 4145 (`...3.1.*` / `...3.6.*`),
  яка допускає рівно два дайджести: ГОСТ 34.311 і Купину-256. Раніше будь-який
  ДСТУ-сертифікат провалювався в `else` з `RET_PKIX_UNSUPPORTED_SIGN_ALG`, тобто
  перевизначити дайджест для ДСТУ 4145 було неможливо взагалі.

**Ключовий момент**: алгоритм підпису **сертифіката** не зобовʼязаний збігатися з дайджестом
самого підпису. У документах Дія сертифікат виданий на ГОСТ-і (`...3.1.1`), а документ
підписаний Купиною (`...3.6.1.1`). Тому гілка узгодженості свідомо не звужує вибір до
одного варіанта — інакше правильна комбінація відхилялася б.

**Парна зміна в Tamga**: `VerifyCmsSignerAt` (`src/lib/core/CryptoniteAdapter.cpp`) прокидає
`SignerInfo.digestAlgorithm` у verify-адаптер через `set_digest_alg`. За RFC 5652 саме це
поле нормативне для дайджесту `signedAttrs`; сертифікат лишається запасним шляхом.
Помилка `set_digest_alg` не фатальна — тоді діє історична поведінка за сертифікатом.

**Перевірено**: повний CTest **34/34** на статичній збірці; обидва PAdES-документи Дія
(LT і LTA) — `SIGNATURE ACCEPTED`, `signatureValid=true`; interop-регресія без змін
(ASiC-E ГОСТ, ASiC-E Купина, ASiC-S, двопідписний CMS Вчасно — ACCEPTED; зламаний
співпідписант — REJECTED).

**Свідоме обмеження**: `sa_sign_data` (шлях **створення** підпису) не змінювався — Tamga
підписує через `SignHash`/власний імпринт, тож Купина на підписанні вже працює й без цього.

**Upstream**: заслати разом із `0006` — це одна прогалина, розділена на дві функції.

### 0008-dstu7564-copy-with-alloc.patch

**Мета**: додати `dstu7564_copy_with_alloc` у сам примітив і зняти fail-closed заглушку,
залишену патчем `0006`.

**Навіщо**: `0006` свідомо повертав `RET_PKIX_UNSUPPORTED_OID` у
`digest_adapter_copy_with_alloc` для режиму Купини, бо upstream `dstu7564` не мав
функції копіювання контексту. Це працювало (споживачів у `pkix` немає), але лишало
Купину єдиним дайджестом без клонування — на відміну від ГОСТ 34.311, SHA-1 і SHA-2,
у яких `*_copy_with_alloc` є. Прогалина в примітиві, а не в адаптері.

**Що змінює**:

- `cryptonite/c/dstu7564.h` / `dstu7564.c` — нова `dstu7564_copy_with_alloc`, за зразком
  наявної `gost34_311_copy_with_alloc`: `memcpy` усієї структури плюс **власна** копія
  `hmac`. `hmac` — єдине поле-вказівник у `Dstu7564Ctx`; без окремого буфера два
  контексти розділяли б одну область і `dstu7564_free` другого дав би double free;
- `pkix/c/crypto/cryptonite_manager.c` — гілка `DIGEST_MODE_DSTU7564` у
  `digest_adapter_copy_with_alloc` тепер клонує контекст замість `SET_ERROR`.

**Перевірено окремим тестом** `TestKupynaContextCopyCarriesState` (`tests/tamga_tests.cpp`):
контекст годується спільним префіксом, потім розгалужується — оригінал добирає `AAAA`,
копія `BBBB`. Перевіряється, що обидва дайджести дорівнюють прямому
`Kupyna(префікс + хвіст)`, тобто копія **несе проміжний стан** і далі не впливає на
оригінал. Дієвість самого тесту підтверджена навмисним псуванням копії (обнуленням
`state`/лічильників) — тест падає з
`the clone must yield Kupyna(prefix+B) ... not a fresh context`.

> Ця перевірка — не формальність. Копія стану геш-функції без тесту дала б рівно той
> клас хибнопозитиву, через який гілку й було спершу закрито: копія з «чистим» станом
> мовчки рахує інший дайджест.

**Перевірено**: повний CTest **34/34** на статичній збірці; interop-регресія без змін.

**Upstream**: заслати разом із `0006`/`0007` — відсутня функція примітиву, не інтеграційна
специфіка Tamga.

### 0009-dstu4145-kupyna-signed-certificates.patch

**Мета**: дати змогу перевіряти підпис СЕРТИФІКАТА, виданого за гілкою `...3.6.*`
(ДСТУ 4145 з Купиною) — доповнення до `0006`/`0007`.

**Навіщо**: `0006` навчив рахувати Купину як дайджест, `0007` — перевіряти нею
підпис даних. Але лишалась третя ситуація: сам **сертифікат підписанта**
виданий на Купині. `verify_adapter_init_by_cert` бере `signatureAlgorithm`
сертифіката і веде його через `check_signature_alg_params`, яка знала лише
гілку `...3.1.*`, тож поверталося `RET_PKIX_UNSUPPORTED_SIGN_ALG` (rc=325) ще
**до** будь-якої криптографії.

Це не теоретичний випадок: так підписаний довірчий список ЦЗО
`TL-UA-DSTU.xml` (`SignatureMethod = dstu4145-dstu7564-256`, підписант
«Адміністратор Довірчого списку» виданий за `...3.6.*`). Через це жива
синхронізація довірчого списку падала цілком — а її перевіряли тільки на
`TL-UA-EC.xml`, який підписаний RSA і проблеми не показував.

**Що змінює** (усе в `crypto/cryptonite_manager.c`):

- `check_signature_alg_params` — гілка `...3.6` дає новий `sa_aid`;
- `create_digest_aid_by_oid` — для неї будується AID Купини-256 (алгоритм не
  параметризований, тож достатньо OID);
- `cryptonite_sign_params_asn_init` — `alg_marker = DSTU4145` для обох гілок:
  це той самий ДСТУ 4145, різниця лише в дайджесті, а параметри ключа
  (`DSTU4145Params`) беруться з SPKI однаково.

**Перевірено на реальних артефактах**: усі три довірчі списки ЦЗО
(`TL-UA.xml`, `TL-UA-DSTU.xml`, `TL-UA-EC.xml`) проходять перевірку підпису;
жива `trust sync` завершується успішно і матеріалізує 83 якорі довіри та 69
сертифікатів TSA; повний CTest 34/34.

**Upstream**: заслати разом із `0006`–`0008` — це одна прогалина підтримки
чинного національного стандарту, розділена по місцях у коді.

### 0010-sha1-context-leak.patch

**Мета**: усунути витік `Sha1Ctx` у двох функціях `crypto/cryptonite_manager.c`.

**Навіщо**: у `sa_sign_data` і `va_verify_data` контекст SHA-1 виділяється через
`sha1_alloc()`, але в блоці `cleanup` звільнювалися лише `sha2_free`,
`gost34_311_free` і (після патчу `0007`) `dstu7564_free`. Виклику `sha1_free`
не було, хоча функція експортується (`cryptonite/c/sha1.h:52`).

**Наслідок до виправлення**: витік на КОЖНІЙ операції підпису або перевірки
шляхом ECDSA-SHA1. Для українського КЕП цей шлях рідкісний, але сесія 1С
довгоживуча, тож витік накопичується протягом роботи застосунку.

**Що змінює**: додано `sha1_free(sha1_ctx);` у `cleanup` обох функцій. Порядок
звільнення в них різний (в `sa_sign_data` `sha2_free` іде перед
`gost34_311_free`, у `va_verify_data` — навпаки), тому вставки зроблено окремо,
а не однією заміною.

**Перевірено**: повний CTest 34/34 на статичній збірці; збірка `vendor=OFF`
не зачіпається (файл до неї не входить).

**Upstream**: очевидний кандидат на надсилання — це чистий дефект upstream, не
Tamga-специфічна інтеграція.

### 0011-rsa-pkix-verify-adapter.patch

**Мета**: підключити наявний RSA-примітив cryptonite до PKIX `VerifyAdapter`
для RSASSA-PKCS1-v1_5 без OpenSSL і платформних API.

**Навіщо**: upstream уже містить повну реалізацію `rsa.c`, але OID-таблиця не
знала `rsaEncryption`/`sha*WithRSAEncryption`, а `CryptoniteSignParams` мав
лише маркери ДСТУ 4145 та ECDSA. Через цю прогалину RSA був недоступний усьому
PKIX-шару, хоча сам примітив працював.

**Що змінює**:

- `api/oids.h` / `api/oids.c` — OID `rsaEncryption` і RSA з SHA-1/256/384/512;
- `crypto/cryptonite_manager.c` — маркер `RSA_PKCS1`, fail-closed DER-розбір
  `RSAPublicKey` із `SubjectPublicKeyInfo.subjectPublicKey`, перетворення `n` і
  `e` у little-endian `ByteArray`, диспетчеризація дайджесту та виклик
  `rsa_init_verify_pkcs1_v1_5` / `rsa_verify_pkcs1_v1_5`;
- `verify_adapter_init_by_cert`, `verify_adapter_init_by_spki`, копіювання й
  digest/set-opt операції адаптера розпізнають RSA без додавання підтримки
  RSA-підписання приватним ключем.

**Межа**: патч додає саме перевірку RSASSA-PKCS1-v1_5. RSA sign/OAEP у PKIX
адаптери не інтегровано, хоча відповідні примітиви існують нижче.

**Перевірено**: прямий primitive-test на реальному `TL-UA-EC.xml` і
`czo-tl-signer.der` (RSA-4096, e=65537), той самий артефакт через
`VerifyAdapter`, негативна однобайтова мутація та паритет із Windows CNG.

**Upstream**: доцільно запропонувати `privat-it/cryptonite`, бо це загальна
прогалина PKIX-адаптера, а не Tamga-специфічна поведінка.

### 0012-msvc-narrowing-conversions.patch

**Мета**: усунути перевірені MSVC C4244 у PKIX і PKCS#12 без глобального
приглушення warning-ів та без зміни форматів даних.

**Що змінює**:

- `pkix_utils.c` — `toupper` отримує значення через `unsigned char` (без UB для
  від'ємного signed `char`), а результат явно повертається до `char`;
- `pkcs12_utils_internal.c` — PKCS#12 diversifier `id` одразу має фактичний
  тип `uint8_t`, який очікує `ba_set`;
- `cryptonite_manager.c` — однобайтовий ECDSA prefix і big-endian байти
  кодуються явними `uint8_t`-перетвореннями; довжина `alg_id_len` лишається
  цілим значенням для індексної арифметики, а звуження відбувається лише при
  записі DER length octet; `wrap_session_key` перевіряє фіксовану довжину
  `rnd_bytes == 64` перед побудовою `SharedInfo`, симетрично до unwrap-шляху,
  щоб довжини гарантовано вкладалися у виділений буфер і DER length octet.

**Межа**: патч не торкається C4701 у OCSP-коді — це окремий дефект FND-009,
який потребує самостійного аналізу життєвого циклу вказівника.

**Перевірка**: чиста MSVC Release-компіляція target-ів `pkix` і `storage`;
warning C4244 у змінених файлах відсутній. Додатково виконується повна
embedded-збірка Tamga з `TAMGA_ENABLE_VENDOR_CRYPTONITE=ON`.

**Upstream**: придатний для надсилання в `privat-it/cryptonite`, оскільки це
типобезпечні виправлення загального C-коду без Tamga-специфічної поведінки.

### 0013-cmake-minimum-version-3.10.patch

**Мета**: прибрати CMake deprecation warnings із embedded-конфігурації без
глобального вимкнення `CMAKE_WARN_DEPRECATED`.

**Що змінює**: `cmake_minimum_required` піднято з `3.5` до `3.10` лише у
шести CMake-файлах, які входять у production vendor build: кореневому
`vendor/cryptonite` та підпроєктах `pthread`, `cryptonite`, `asn1`, `pkix`,
`storage`.

**Сумісність**: Tamga вимагає CMake 3.23 або новіший, тому ця зміна не звужує
підтримуване середовище Tamga. CMake 3.10 достатньо новий, щоб сучасний CMake
не вмикав застарілі policy compatibility режими, але не змінює target-и чи
прапори компіляції vendor-коду.

**Перевірка**: чистий embedded configure з
`TAMGA_ENABLE_VENDOR_CRYPTONITE=ON` завершується без шести попередніх
`Compatibility with CMake < 3.10` deprecation warnings; patch проходить
reverse-apply check разом із `0012`.

**Upstream**: придатний для надсилання в `privat-it/cryptonite` як механічне
оновлення мінімальної підтримуваної версії CMake.

### 0014-msvc-warning-isolation-and-wide-path.patch

**Мета**: ізолювати відомий warning-noise upstream від first-party warning
policy Tamga, не приховуючи потенційно небезпечні неініціалізовані
локальні змінні.

**Що змінює**:

- на MSVC `CRYPTONITE_STRICT_WARNINGS=ON` вмикає `/W4`, а embedded-режим
  `OFF` використовує `/W1` з явно ввімкненими `C4701` і `C4703`;
- на GCC/Clang `-Wall -Werror` застосовуються лише для standalone strict-збірки;
  embedded-режим не успадковує first-party warning flags Tamga;
- `dirent_internal.c` явно викликає `GetFileAttributesW` для створеного
  `wchar_t`-шляху. Це прибирає некоректний cast до `LPCSTR` і робить
  поведінку незалежною від макросів `UNICODE` батьківського проєкту.

**Межа**: `C4701`/`C4703` не вимкнені й не виправляються цим патчем.
Конкретний C4701 в `ocsp_response_engine.c` лишається FND-009; інші
спрацювування в upstream-файлах є окремим vendor warning debt і мають
бути проаудитовані до формування вузького allowlist.

> **Стан цієї межі (Н-11, 2026-08-27): борг закрито.** FND-009 виправлено
> патчем `0015`, решту дев'ять спрацювань проаудитовано поштучно й виправлено
> патчем `0016`. Allowlist не знадобився: жодне попередження не глушиться,
> усі виправлені за причиною. Одне зі спрацювань (`ANY.c`) виявилося справжнім
> дефектом — `free()` неініціалізованого вказівника.

**Перевірка**: чиста embedded MSVC Release-збірка: first-party цілі
мають `/W4`, vendor-цілі — `/W1 /w14701 /w14703`, `miniz` — `/W0`;
`C4701` залишається в лозі, а `D9025`, масові `C4244` і `C4133` в
`dirent_internal.c` відсутні.

**Upstream**: виправлення wide-path придатне для upstream; warning-режим
є інтеграційною політикою embedded-збірки Tamga.

### 0015-ocsp-response-error-path-ub.patch

**Мета**: усунути UB у помилкових шляхах формування OCSP response (FND-009),
який MSVC також діагностував як C4701.

**Що змінює**:

- `eocspresp_generate` та `eocspresp_form_unauthorized` zero-initialize
  `OCSPResponseStatus_t` до першого `CHECK_PARAM`;
- caller output зануляється перед перевірками;
- cleanup `unauthorized` звільняє локальний `ocsp_response`, а не потенційно
  неініціалізований caller-owned `*resp`, і використовує ASN content-free helper;
- upstream unit test додає негативний виклик `eocspresp_form_unauthorized(NULL)`.

**Перевірка**: Tamga regression викликає invalid `eocspresp_generate`,
`eocspresp_form_unauthorized(NULL)` і успішне формування/звільнення response;
окремо перевіряється clean compile зміненого TU без C4701 та reverse-apply patch.

**Upstream**: патч не містить Tamga-специфічної поведінки й придатний для
надсилання в `privat-it/cryptonite` разом із негативним unit test.

### 0016-msvc-uninitialized-locals-and-pointer-cast.patch

**Мета**: закрити залишковий vendor warning debt, який `0014` свідомо лишив
відкритим (`C4701`/`C4703` «не вимкнені й не виправляються цим патчем»), і
прибрати truncating pointer cast. Після цього embedded MSVC-збірка vendor-цілей
дає **нуль** попереджень.

**Що змінює** (8 файлів, 12 рядків):

- `asn1/c/ANY.c` — **справжній дефект, не хибне спрацювання.** `CHECK_PARAM`
  стрибає на `cleanup` до `memset(&tmp, ...)`, а `cleanup` викликає
  `FREEMEM(tmp.buf)` — тобто `free()` неініціалізованого вказівника при
  `ANY_new_fromType(NULL, ...)`. `memset` перенесено перед `CHECK_PARAM`.
  Це той самий клас дефекту, що виправив `0015` в `ocsp_response_engine.c`;
- `cryptonite/c/dstu4145.c`, `cryptonite/c/ecdsa.c` — `verify_comb_opt_level`
  і `verify_win_opt_level` зануляються при оголошенні. Читання відбувається
  лише під `need_update_precomp_q`, і в кожній гілці, де прапорець істинний,
  змінні присвоєні, — MSVC цю кореляцію не доводить;
- `cryptonite/c/dstu7624.c` — `shift_key_size = 0` (читання в `cleanup`
  захищене `if (key_shift_ptr)`, але недоказово для компілятора);
- `asn1/c/INTEGER.c` — `dec_value = 0` (присвоюється на шляхах `ST_END_ENUM`
  і `ST_DIGITS`, недоказово через state machine);
- `asn1/c/constr_SET.c` — `t2m_count = 0` (корелює з `t2m_build_own`);
- `asn1/c/ber_decoder.c` — `tlv_len = 0`. Тут інваріант «цикл виконається
  хоча б раз» тримався **лише на `ASSERT`, який у релізі є порожнім макросом**
  (`stacktrace.h:19`), тож `*last_length = tlv_len` міг віддати виклику сміття.
  Патч не змінює жодного дозволеного `ASSERT`-ом шляху, а робить значення
  детермінованим;
- `asn1/c/per_support.c` — `(long)pd->buffer` (C4311: на Win64 `long` 32-бітний,
  вказівник 64-бітний) замінено на `(long)((uintptr_t)pd->buffer & 0xf)`:
  маскування виконується в `uintptr_t`, і лише результат 0..15 звужується.
  Виправлено обидва входження — у `snprintf` і в `ASN_DEBUG`.

**Перевірка**: чистий rebuild vendor-цілей у embedded MSVC Release — було
10 попереджень (9× `C4701`, 1× `C4311`), стало 0; reverse-apply check патча
проходить; повні сюїти `48/48`, `33/33`, `32/32`.

**Upstream**: Tamga-специфічної поведінки немає, патч придатний для надсилання
в `privat-it/cryptonite`. Найцінніша частина для upstream — `ANY.c`, бо це
реальний `free()` неініціалізованого вказівника.

### 0017-any-c-trailing-blank-line.patch

**Мета**: описати чергою відхилення, яке чергою не описувалося.

**Навіщо**: `src/asn1/c/ANY.c` в upstream закінчується на `}\n\n`, а в
`vendor/cryptonite` — на `}\n`. Порожній рядок зник ще при першому імпорті
знімка і не був оформлений жодним патчем. Функціонального впливу немає, але
доти будь-який механічний replay падав саме на цьому файлі, тобто
невідтворюваність черги трималася на одному невидимому байті.

**Знайдено**: 2026-08-30, першим прогоном `scripts/verify-cryptonite-patches.ps1`
(до цього черга ніколи не відтворювалася з чистого upstream).

**Upstream**: не надсилати — це не покращення, а фіксація локальної косметики.

## Робота з чергою

### Пін upstream

Джерело істини — `patches/cryptonite/upstream.json`:

| поле | значення |
| --- | --- |
| `url` | `https://github.com/privat-it/cryptonite` |
| `commit` | `3618d340d22e27a6becf97d89c453f8e64068a39` |
| `ref` | `refs/heads/master` (стан на 2026-08-30) |

`vendor/README.md` посилається на той самий пін. Оновлювати SHA можна **лише**
разом із перезняттям знімка і повторним прогоном replay.

### Порядок застосування

Порядок = порядок рядків у `series.txt`, зверху вниз, без пропусків.
Патчі не комутативні: `0007`, `0009`, `0010`, `0012` торкаються того самого
`crypto/cryptonite_manager.c`, а `0013` і `0014` — того самого
`CMakeLists.txt`.

У черзі **два різні корені шляхів** — історична, але істотна деталь:

- `0001`–`0005` — шляхи від кореня cryptonite (`a/CMakeLists.txt`) → `-p1`;
- `0006`–`0017` — шляхи від кореня Tamga (`a/vendor/cryptonite/CMakeLists.txt`)
  → `-p3` при накладанні всередині каталогу cryptonite.

Тому єдиної команди `git am patches/cryptonite/*.patch` не існує. Скрипт
визначає рівень `-p` із самого патча (за наявністю префікса `vendor/cryptonite/`)
і падає, якщо в одному патчі корені **змішані**.

### Механічна перевірка

```powershell
pwsh -File scripts/verify-cryptonite-patches.ps1
```

Скрипт: читає пін → тягне чистий знімок (`git fetch --depth 1` на конкретний
SHA) → звіряє отриманий SHA з піном → накладає `series.txt` по черзі →
побайтово порівнює результат із `vendor/cryptonite`. **Успіх = порожній diff.**

Корисні параметри:

- `-SnapshotDir <шлях>` — узяти знімок із кешу замість мережі;
- `-Offline` — заборонити мережу (без `-SnapshotDir` скрипт одразу падає);
- `-KeepWorkDir` — лишити дерево replay для розбору розходження.

Різниця лише в переводах рядків (`CRLF` проти `LF`) звітується окремо і **не**
вважається розходженням: вона залежить від `core.autocrlf` на машині, а не від
черги. На Linux-раннері таких файлів 0, на Windows із `core.autocrlf=true` —
близько тисячі.

### Що робити, коли патч не накладається

Скрипт назве конкретний файл і рівень `-p`. Далі, за спаданням імовірності:

1. **Правку внесено прямо у `vendor/cryptonite` повз чергу.** Найчастіший
   випадок. Не відкочувати vendor вручну: зняти різницю
   (`git diff` між replay-деревом і vendor) і додати її **новим** патчем у
   кінець `series.txt`. Саме так зʼявився `0017`.
2. **Патч зіпсований.** Класична пастка — неправильні лічильники в заголовку
   гунка `@@ -a,b +c,d @@`: `git apply` мовчки бере рівно `d` рядків і
   **обрізає решту**, не повідомляючи про помилку. Так `0003` роками давав
   `src/pthread/CMakeLists.txt` без `endif()` — файл із синтаксичною помилкою
   CMake, і ніхто цього не бачив, бо застосовану версію ніхто не перевіряв.
   Перегенеруйте патч `git diff`, не правте лічильники на око.
3. **Зміщено пін upstream** (`upstream.json`). Перевірте
   `git ls-remote <url>` і чи існує ще пінований коміт.
4. **Конфлікт після оновлення upstream.** Накладайте серію по одному патчу,
   перегенеровуйте той, що конфліктує, і **не** зливайте два патчі в один:
   іменована черга цінна саме тим, що кожне відхилення має власне
   обґрунтування в цьому README.

Новий патч завжди додається **в кінець** `series.txt` і описується розділом у
цьому README. Скрипт падає, якщо файл є в каталозі, але його немає в
`series.txt` (або навпаки).

### Збірка

Механічна рівність дерев не доводить, що дерево збирається. Після replay:

```bash
cmake -B build -DTAMGA_ENABLE_VENDOR_CRYPTONITE=ON
cmake --build build
# Очікуємо: cryptonite, asn1, pkix, storage, pthread_impl зібрані,
#           тестові targets НЕ створені (їх вимикає 0001)
```

### 0018-dstu4145-kupyna-sign-adapter.patch

**Мета**: навчити ПІДПИС рахувати Купину — дзеркало патча `0007`, який зробив
це для перевірки.

**Симптом**: підпис ключем ДСТУ 4145, чий сертифікат виданий з Купиною
(`1.2.804.2.1.1.1.1.3.6.1.1` — норма для сертифікатів після переходу ЦЗО на
ДСТУ 7564), не проходив перевірку: `SIGNATURE_CRYPTOGRAPHICALLY_INVALID`.

**Причина**: `sa_sign_data` у гілці DSTU4145 беззастережно хешував ГОСТ 34.311,
тоді як `digest_adapter_init_by_cert` (патч `0006`) для такого сертифіката
віддає Купину. У CMS `digestAlgorithm` і `signatureAlgorithm` казали «Купина», а
підписувався геш ГОСТ — контейнер виходив внутрішньо суперечливим.

**Зміни**: у `sa_sign_data` дайджест обирається за гілкою `signature_aid`
(`...3.6.*` -> Купина, інакше ГОСТ 34.311), додано `Dstu7564Ctx` і його
звільнення. Джерело рішення те саме, що в `0006`: тип ключа (`...3.1.1`)
однаковий для обох поколінь, тож розрізняє лише алгоритм підпису сертифіката.

**Перевірка (2026-09-02)**: реальний ключ `.ZS2` ЦСК «Україна» із сертифікатом
епохи Купини — `sign-file` -> CMS 2491 Б, `verify-file` -> `valid`; контроль на
ключі КНЕДП «Вчасно» із сертифікатом епохи ГОСТ лишився `valid`.

### 0019-support-kalyna-kupyna-pkcs5.patch

**Мета**: нативно розбирати PKCS#12/`.ZS2` АЦСК «Україна», де PBES2
використовує KMAC Купина-256 (`1.2.804.2.1.1.1.1.2.2.4`) і Калина-256 CBC
(`1.2.804.2.1.1.1.1.1.3.5.2`).

**Симптом**: `pkcs12_decode` завершувався
`RET_STORAGE_UNSUPPORTED_ENC_SCHEME_ALG` (`rc=536`), тому бібліотека не могла
перебрати обидва ключі контейнера `DU...ZS2` і зіставити ключ підпису із
зовнішнім сертифікатом.

**Зміни**: зареєстровано обидва OID; до HMAC-інтерфейсу додано KMAC ДСТУ 7564;
до PBKDF2-подібного циклу — 32-байтовий ключ пароля й Купину-256; до cipher
adapter — Калина-256 CBC із перевіреним PKCS#7-паддингом. Після цього звичайний
PKCS#12-шлях може декодувати всі `pkcs8ShroudedKeyBag`, а наявний відбір за
відповідністю `Q_key == Q_cert` і `keyUsage` обирає ключ підпису.

**Перевірка (2026-09-03)**: патч зібрано MSVC x64 з `/W4 /WX`; остаточні
команди replay, CTest і підписання реального `.ZS2` наведено в
`docs/bugfix-log.md` після завершення релізної перевірки.

### 0020-rsa-verify-signature-size.patch

Перевірка RSA PKCS#1 v1.5 відхиляє підпис, довжина якого не дорівнює довжині
модуля, та представник підпису поза діапазоном `[0, n)`. Перед розбором padding
перевіряється мінімальний розмір блока. Це зберігає передумови арифметики
`WordArray`: добір хибного RSA-видавця іншої розрядності не повинен доходити
до операцій із несумісними розмірами буферів. Регресії —
`tamga-rsa-cryptonite-primitive-tests` — pass (2026-09-04); повторна перевірка
реального PDF — 100/100 без аварій. Це історичні результати 2026-09-04; поточний випуск перевіряється заново за `docs/release-process.md`.
